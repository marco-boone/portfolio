## The problem

In a simple in-order pipeline, one slow load (like a cache miss) stalls every instruction behind it, even ones that don't depend on it. An out-of-order core runs ready instructions early and commits them in program order, so the program still behaves correctly.

<OooTimeline>One load misses in the cache. In order, the independent `mul` and `sub` stall behind it. Out of order, they run during the miss and the program finishes 2 cycles sooner.</OooTimeline>

## Architecture

The core is split into a front end that fetches and decodes, a middle that renames registers and tracks instructions, and a back end that executes them and commits results in order.

<OooPipeline>Instructions flow down each column, left to right. Finished results are broadcast on the common data bus (CDB), which wakes up instructions waiting in the reservation stations.</OooPipeline>

## Key features

{/* FILLER: confirm against the final design */}
- Register renaming with a map table and free list, R10K-style
- Reorder buffer (ROB) for in-order commit and precise exceptions
- Reservation stations that issue instructions as soon as their operands are ready
- Branch prediction with a BTB, and recovery on a mispredict
- Load/store queue for memory ordering
